The Fiducia Language Reference

Introduction

This is the reference for Fiducia, the source language consumed by the fic compiler. A Fiducia source tree describes a seL4 Microkit system: its memory regions, protection domains, channels, the per-PD program logic, and the communication / computation events those programs orchestrate.

Fiducia has two layers. The orchestration layer is written in Fiducia itself: it says which channel events occur in a protection domain and in what order, and fic generates the event loop and every Microkit call from it. The computation layer is foreign code (C or Pancake) that the orchestration calls from computation events; it holds the data flow. Orchestration communicates; foreign functions compute. The two meet at a narrow boundary that the compiler checks and the verifier reads.

The reference is organised after the Rust Reference: each chapter pairs a formal grammar production with the prose semantics that surround it, then expands per syntactic feature with focused subsections and short examples. Where the surface syntax is still in flight, the chapter calls out the incomplete forms with a 🚧 marker so the reference stays honest about what the parser actually accepts today.

Source surfaces

A Fiducia project is one directory holding the files the compiler reads together:

  • System description (.fis) — the static topology: the data layer (struct and const items), memory regions, protection domains, channels, the system composition. One per project; it is the project.
  • Program implementations (.fi) — per-PD orchestration: imports of foreign C / Pancake files, memory mappings, program variable declarations, evt declarations, and proc definitions. One per protection domain.
  • Foreign implementations (.c, .h, .pnk) — the code a .fi imports. Not Fiducia source, but its signatures and contracts are read.

The .fis and the .fi files are linked by name. Each protection domain p declared in the .fis is implemented by p.fi beside it: a PD without that file is an error at its declaration, and so is a PD declared twice; a .fi that no PD names is a warning and is never read. Within a program, a Mapping refers to a MemoryRegion declared in the .fis; a channel reference in a process expression resolves against the .fis channel declarations; a computation event referenced by name from a process is declared in the same .fi with evt. The Project Layout chapter gives the full rules.

What the compiler does with a project

fic reads the sources, resolves every name, types the result and runs the checks, then lowers each protection domain’s orchestration once into a control-flow graph that every backend reads. From that graph it produces:

  • a bootable Microkit image: generated C per protection domain, built with the foreign code and assembled with the generated system description; and
  • a system model for UPPAAL, in which each protection domain is one template and each foreign function’s contract stands for its body, so that queries about the whole system (deadlock freedom, ordering, reachability) can be model-checked.

The same checks run whichever output is asked for. Running the model checker and the code verifiers, and building and launching the image, are covered by the manual; this reference covers the language those tools read.

🚧 Type checking and well-formedness checking are not yet complete: the chapters on well-formedness and information flow state exactly what is checked today.

Notation

This reference uses a BNF dialect for grammar productions. The notation is intentionally close to the Rust Reference so readers familiar with Rust documentation can read it without a separate primer.

Grammar productions

A production has the form LHS ::= RHS, where the right-hand side is a sequence of terminals, non-terminals, and meta-operators. Productions are written in text-tagged code blocks:

EventDecl ::= 'evt' ident carriers? ':' (stmt | '{' stmt* '}')
carriers  ::= carrier_group+
carrier_group ::= '.' '|' param (',' param)* '|'
param     ::= ident ':' type

Meta-operators

'literal'A literal token (keyword, symbol). Matches verbatim.
identAn identifier: an ASCII letter or _, then letters, digits or _, and not a reserved keyword.
UIdentAn ident whose first character is an uppercase ASCII letter (UpperCamelCase); process names and references.
UPPER_IDENTAn ident written in upper case by convention (constants such as SLOT_SIZE); the parser accepts any ident.
X?Zero or one of X.
X*Zero or more of X.
X+One or more of X.
X | YEither X or Y. Listed alternatives appear on separate lines for readability when the disjunction is long.
(X Y)Grouping; otherwise meta-operators bind tighter than juxtaposition.

Literals in a production are named by their lexical class (the lexical structure has the full rules):

Comments inside a production start with --; examples, which are Fiducia source, use the language’s own // and /* */.

Whitespace between symbols in a production is significant only when called out — most productions allow inter-token whitespace and comments, exactly as the lexer does.

Inline references

  • A non-terminal in prose is written in italics (e.g. event, process).
  • A literal token in prose is written in backticks (e.g. Event, ->).
  • A type-level reference into the AST uses backticks plus the Rust path fragment when it disambiguates (Event::CPEvent, Process::Choice { branches, default }).

Examples

Examples render in text-tagged code blocks, not rust-tagged: the Fiducia source language is not Rust, and text keeps mdBook’s syntax-highlighter neutral. Example:

evt handle_irq:
    eth.handle_irq();

Where an example references symbols declared elsewhere (a channel from the .fis file, a function from an imported .c file, a process declared in the same section), the surrounding prose names the dependency.

Lexical Structure

A .fis and a .fi file are ASCII text read with the same lexer. This chapter fixes the words the grammars use: what separates tokens, what a name is, which words are reserved, and how literals are written.

Whitespace and comments

Spaces, tabs and newlines separate tokens and are otherwise ignored. Comments count as whitespace:

// A line comment runs to the end of the line.
/* A block comment runs to the first closing star-slash. */

Block comments do not nest: /* a /* b */ c */ ends at the first */, and c */ is then read as source.

Identifiers

ident  ::= (letter | '_') (letter | digit | '_')*   -- not a reserved word
UIdent ::= ident whose first character is an uppercase letter

letter and digit are ASCII. Case matters. A word that merely starts with a reserved word is an identifier: irq_count and Mapping_x are names.

UIdent is what a process is called, in its proc declaration and at each reference to it (Notified, Drain(x)). Everything else (variables, events, parameters, mappings, memory regions, protection domains, channels, structs, constants) takes any ident; the upper and lower case styles in the other chapters are conventions the parser does not check.

Reserved words

A reserved word is not an identifier, so none can name a variable, event, mapping, region, protection domain, channel, struct or constant.

GroupWords

Program itemsimport, as, Mapping, irq, evt, proc, default, dbg

void is reserved so it cannot be read as a struct name; Fiducia has no void type and no pointers (see Types).

sizeof is not on the list: a variable may be named sizeof. In an expression, sizeof( followed by a type is the size operator (see Expressions).

microkit, init and notified are ordinary identifiers; they have meaning only inside an @bind annotation (see Entry Points). Likewise packed, inside an @attr annotation (see Data Layer).

Literals

A leading - is never part of a literal: -5 is the unary minus applied to 5, which the compiler folds to one constant. There are no binary, octal, character or floating-point literals.

An import path is not a text literal: it is any characters between the quotes, up to the closing " or the end of the line.

Punctuation

The process algebra’s operators are -> (event prefix), --> and <-> (channel directions), ||| (interleave), [] (choice), ! (send), ? (receive) and ; (sequence); @ introduces an annotation. The expression operators and their precedence are in Expressions.

Types

Type     ::= BaseType ('[' ArrayLen ']')?
BaseType ::= ScalarType | ident            -- ident names a declared struct
ScalarType ::= 'bool' | 'byte' | 'Address'
             | 'int'  | 'int8'  | 'int16'  | 'int32'  | 'int64'
             | 'uint' | 'uint8' | 'uint16' | 'uint32' | 'uint64'
ArrayLen ::= int_lit | ident               -- ident names a declared constant

Every variable, parameter, carrier, struct field and constant has a type written this way. Fiducia has no pointer types and no void type.

Scalars

TypeMeaning

int, uint and byte are other names for int64, uint64 and uint8: the same types, not conversions of them. The data layer still rejects int and uint in a struct field, since they name no fixed size there; use the sized types.

Address is the type of a mapping’s m.vaddr and m.paddr (see Imports and Mappings).

Structs and arrays

A struct is declared in the .fis’s data layer and is visible to every program by name. A fixed array T[N] holds N elements of one type; N is an integer literal or a declared constant, and a type has at most one array suffix: T[N], never T[N][M].

const LEN: uint = 4;

struct Header {
    kind:  uint8;
    seq:   uint8;
    flags: uint16;
}

struct Frame {
    head: Header;
    data: byte[4];
}

done:  bool;
raw:   byte;
level: int8;
count: uint;
frame: Frame;
codes: uint16[LEN];

sizeof(T) is the size of any type in bytes, a constant: sizeof(Frame), sizeof(uint16[LEN]). A struct’s fields are laid out as C lays them out, in declaration order and padded, unless the struct is @attr(packed) (see Data Layer).

A struct or array variable is assigned whole. A field of a struct value is read with x.f (frame.head.kind); a field cannot be assigned to, and there is no indexing of an array element in a .fi. A channel’s slot type is a struct or a scalar, never an array (see Channel Declarations).

Conversion

There are no implicit conversions. Both operands of an arithmetic, bitwise or comparison operator have one type, and a literal takes the type of the operand beside it. An assignment must match the type of the variable it assigns exactly: a = raw is an error for an int a and a byte raw.

The one conversion is the cast e as T:

done  = step > 0;
level = step as int8;
count = step as uint + 1;
raw   = frame.head.kind as byte;
  • The target T is an integer type or Address; the operand is an integer or an address. A bool, a struct and an array can be neither.
  • as binds tighter than the binary operators and looser than the unary ones, so step as uint + 1 is (step as uint) + 1 (see Expressions).
  • A narrowing cast of a constant is not a constant overflow: 300 as uint8 type-checks as a uint8, where a bare 300 would not fit.
  • Unary - is defined only on signed types; ! only on bool.

Project Layout

A Fiducia project is one directory. The compiler is given that directory and reads these files from it:

datadiode/
    datadiode.fis     the system: one per project
    eth_outer.fi      the program of protection domain eth_outer
    dd.fi             the program of protection domain dd
    eth_inner.fi      the program of protection domain eth_inner
    fire.toml         read by fire, not by fic

The .fis

The directory holds exactly one .fis; it is the project. Its name is free, and a directory with none, or with two, is an error. Everything the system declares (the data layer, regions, protection domains, channels and the System composition) is in it.

The .fi files

Each protection domain p is implemented by p.fi, in the same directory as the .fis: the file name is the binding, and nothing inside either file names the other. The directory is read for .fi files, not searched below:

  • A protection domain with no p.fi is an error at its declaration in the .fis, and so is a protection domain declared twice.
  • A .fi that no protection domain names is a warning, and the file is never parsed.
  • A .fi in a subdirectory is not seen.

Imports

An import path is relative to the project directory, not to the .fi that writes it, so import "include/eth.h" as eth; reads datadiode/include/eth.h from any program in the project. The extension picks the reader: .c and .h are C, .pnk is Pancake.

Generated files

Compiling writes under the project directory, and nothing outside it unless -o says so:

Data Layer: Structs and Constants

StructDecl ::= Attr? 'struct' ident '{' Field* '}'
Attr       ::= '@attr' '(' 'packed' (',' 'packed')* ')'
Field      ::= ident ':' Type ';'
Type       ::= BaseType ('[' ArrayLen ']')?
BaseType   ::= ScalarType | ident            // ident names a declared struct
ArrayLen   ::= integer-literal | ident       // ident names a declared constant
ConstDecl  ::= 'const' ident ':' Type '=' Expr ';'

The data layer is the system-wide vocabulary of payload struct types and layout constants. It is shared by every protection domain — and, through generated type headers, by the external low-level implementations (C, Rust, Pancake) too, so the model and the code agree on one definition. It lives as flat, top-level items in the .fis file: like the rest of the system description, declarations are visible to every .fi program with no import ceremony.

const PACKET_BUFFER_SIZE: int = 2 * 1024;

struct Packet {
    length:  uint16;                    // valid bytes in payload (≤ capacity)
    payload: byte[PACKET_BUFFER_SIZE];  // fixed-capacity buffer
}

const RING_BYTES: int = 64 * sizeof(Packet);

Structs

  • Names use UpperCamelCase by convention.
  • Fields are flat — primitives, other declared structs, or fixed-size arrays of those; no pointers.
  • Fixed-size arrays T[N]: the length N is an integer literal or a declared integer const (e.g. byte[PACKET_BUFFER_SIZE]), so the size stays statically known: sizeof(T[N]) = N * sizeof(T).
  • No recursion: a struct may not contain itself, directly or indirectly. This guarantees sizeof is computable at compile time by recursive field traversal.
  • Fields must have fixed-width types so the layout is well-defined: int, uint and Address have no fixed size and are rejected in a struct (uint32, not uint), as is a struct nesting one that has none. An array has one length: T[N], not T[N][M].
  • Field names within a struct are distinct.
  • Layout is C’s on the target, fields in declaration order: each field at the next offset that is a multiple of its alignment (a scalar’s is its size, an array’s its element’s, a struct’s its largest field’s), and the size rounded up to the struct’s alignment, so { a: uint64; b: uint16; } is 16 bytes with b at 8. The generated headers assert it (a _Static_assert on each struct’s size in types.h), so a C compiler that would lay the struct out differently fails the build.
  • @attr(packed) before struct packs it, as C’s __attribute__((packed)): no padding, each field right after the one before, alignment 1, so @attr(packed) struct W { a: uint8; b: uint32; } is 5 bytes with b at 1. A struct nested in it keeps its own padding. Packing is for wire formats: a misaligned field is slower to read, and on device memory or under an atomic, an aarch64 fault.
  • Struct names are usable wherever a type is expected — variable declarations, typed channel buffers (via buf<Packet>), and sizeof.

Constants

  • Names use SCREAMING_SNAKE_CASE by convention (any identifier is accepted); a declared type is required. Unlike a struct field, a constant may have an unsized type such as int or uint.
  • The right-hand side is a full expression, folded at compile time (rustc-style, before any lowering). The const subset covers: literals, references to previously declared constants, sizeof(T), and unary/binary arithmetic, bitwise, shift, comparison, and logical operators.
  • Function calls, runtime variables, and field access are rejected in const position. Forward references between constants are errors — declare in dependency order.
  • The folded value must match the declared type (bool constants take boolean values; integer-family types take integers).

One home for structs

Every struct is declared in the .fis. A program names them as any other type, for its locals and body variables, and so do the C and Pancake files it imports.

fic writes the structs and constants to include/gen/types.h (and, for Pancake, include/gen/types.pnk), included as "gen/types.h" with <project>/include on the include path.

Global state

The data layer declares types and constants, not mutable state. A program’s own variables are its protection domain’s state (see Variable Declarations); state shared across domains is exactly the channel-buffer view: mutable data lives in declared memory regions, mapped explicitly into the PDs that may touch it and labelled for information flow. A shared scalar is a typed slot of a declared region — never an ambient global.

Memory Region Declarations

MemoryRegionDecl ::= SecurityLabel? 'MemoryRegion' ident '(' size (',' page_size)? (',' phys_addr)? ')' ';'
size             ::= hex
page_size        ::= hex      // '0x1000' (4 KiB) | '0x200000' (2 MiB)
phys_addr        ::= hex
SecurityLabel    ::= 'High' | 'Low'

A memory region declaration introduces one named region of physical or virtual memory that protection domains can later map into their address space. MemoryRegion declarations live in .fis system files; they are pure topology and carry no per-PD program logic.

Fields

  • Security label (optional, defaults to Low). Tags information-flow level. The one rule is on mappings: a mapping’s label must be at least its region’s, so a High region is never mapped at Low; protection domains carry no labels. See Information-flow labels; the Information Flow chapter covers the check.
  • Name — snake_case identifier; the same name is referenced from Mapping declarations in .fi files.
  • Size — required, hex literal, in bytes. Must be a multiple of the region’s page size; the parser rejects a size that is not.
  • Page size — optional, defaults to 0x1000 (4 KiB). The other accepted value is 0x200000 (2 MiB / Large). The slot may be left empty to give a physical address alone (MemoryRegion mmio(0x1000, , 0xfe000000);), and any other value is not an error: it silently falls back to 4 KiB, so a mistyped page size changes which alignment is checked.
  • Physical address — optional. When present, must be aligned to the region’s page size. Used for device MMIO regions (clock controller, ethernet registers) where the seL4 loader maps a fixed physical frame rather than allocating one.

Security label and ordering

The label, if present, comes before the MemoryRegion keyword. Omitting it is equivalent to writing Low:

MemoryRegion ring_buffer_outer(0x1000, 0x1000);          // Low (default)
Low MemoryRegion eth0(0x10000, 0x10000, 0x5b040000);     // explicit Low
High MemoryRegion ring_buffer_inner(0x1000, 0x1000);     // High
High MemoryRegion eth_clk(0x1000, 0x1000, 0x5b200000);   // High MMIO

Validation

Two checks run in the parser, each reported at the declaration:

  1. size is a multiple of page_size.
  2. phys_addr (if present) is aligned to page_size.

Resolution then checks that the region name is unique within the system file. A region is referenced from .fi files by its name; the validator confirms each Mapping’s mem_region points at a declared MemoryRegion.

Channel buffers

A region named in a channel’s via clause is a channel buffer. It is mapped into both endpoint PDs implicitly, backs one channel only, and must not also appear in an explicit Mapping; each of these is an error otherwise. Any other region may be mapped by several PDs.

Examples

// Anonymous shared buffer, default 4 KiB page, allocator-assigned phys_addr.
MemoryRegion ring_buffer_outer(0x1000, 0x1000);

// 2 MiB region — large pages, allocator-assigned phys_addr.
MemoryRegion packet_buffer_outer(0x200000, 0x200000);

// Memory-mapped device (4 KiB MMIO, fixed physical address).
Low MemoryRegion eth_outer_register(0x1000, 0x1000, 0xf000000);

// 64 KiB device register window.
Low MemoryRegion eth0(0x10000, 0x10000, 0x5b040000);

// High-side region (a `Low` mapping of it is rejected by the
// information-flow check).
High MemoryRegion eth_clk(0x1000, 0x1000, 0x5b200000);

Protection Domain Declarations

ProtectionDomainDecl ::= 'ProtectionDomain' ident '(' priority (',' irq?)? (',' budget?)? (',' period?)? ')' ';'
priority             ::= integer_literal       // 0 ≤ p ≤ 254, enforced
irq                  ::= integer_literal       // fits u16; range not enforced
budget               ::= integer_literal       // microseconds, default 1000
period               ::= integer_literal       // microseconds, default = budget

A protection-domain declaration introduces one named seL4 Microkit protection domain (PD): an isolated thread of execution with its own address space, scheduling parameters, and (optionally) one IRQ binding. Each ProtectionDomain listed in a .fis system file pairs with one .fi program file, <name>.fi beside the .fis.

Fields

  • Name — snake_case identifier. The matching <name>.fi file holds the PD’s mappings, events, and processes.
  • Priority — required, range 0..=254 (it is read as a u8 below 255). Out-of-range values are rejected with a parse-time error. Higher numbers run first under the Microkit fixed-priority scheduler.
  • IRQ — optional; any value fitting a u16 parses (no range check is enforced by the compiler — pick a number the target board’s IRQ controller actually has), but one IRQ may be claimed by only one PD. When present, the PD is wired to receive that hardware interrupt on the reserved irq channel and can observe it via irq?N / irq!N events.
  • Budget — optional, microseconds; defaults to 1000. Microkit schedules the PD for at most budget microseconds out of every period.
  • Period — optional, microseconds; defaults to whatever budget was set to. Setting period > budget produces a sub-rate scheduling policy.

The trailing fields are positional, and any of them may be left empty to set a later one: ProtectionDomain pd(100, , 500); sets the budget with no IRQ, and ProtectionDomain pd(100, , , 2000); the period alone.

Validation

  • priority must be in 0..=254.
  • A PD name is unique within the system file; a second declaration is an error at the later one.
  • An IRQ number belongs to one PD.
  • A PD that is referenced from a Channel or from the System = composition must be declared.
  • A PD without a <name>.fi beside the .fis is an error when the project is loaded, not when the .fis is parsed. A .fi that no PD names is only a warning, and the file is never opened.

Examples

// Three PDs with distinct priorities; IRQ on the outer driver only.
ProtectionDomain eth_outer(99, 159);
ProtectionDomain dd(150);
ProtectionDomain eth_inner(199, 155);

// A simulator with a low priority and no IRQ binding.
ProtectionDomain simulate(50);

// Explicit budget / period pair (sub-rate scheduling).
ProtectionDomain monitor(120, 0, 200, 1000);  // priority 120, IRQ 0, 200 µs / 1 ms

System composition

A .fis file ends with a System = ... clause that names the PDs to include, joined by the interleave operator |||, the only composition. Every PD referenced in System must be declared above:

System = eth_outer ||| dd ||| eth_inner ||| simulate;

PDs declared but omitted from System are dead code and currently produce no error; this may tighten in a future revision.

Channel Declarations

ChannelDecl       ::= SyncChannelDecl | AsyncChannelDecl

SyncChannelDecl   ::= 'Sync' 'Chan' ident '=' ident '-->' ident ';'?

AsyncChannelDecl  ::= 'Async'? 'Chan' ident '=' ident '-->' ident ViaClause? ';'?
                    | 'Async'? 'Chan' ident '=' ident '<->' ident ';'?

ViaClause         ::= 'via' ident '<' Type (',' Capacity)? '>'
Capacity          ::= int | ident          -- a literal or a const

A channel declaration introduces one named communication endpoint between two protection domains. Channels live in .fis system files; the .fi files reference them by name only, in the channel events of a process.

A channel is one of two kinds:

  • a signalling channel carries no value: a send c! wakes the other side, and a receive c? waits for it;
  • a message-passing channel carries values of a type: a send c!e passes the value of e, and a receive c?x binds it to x. Today the one message-passing channel is the buffered channel; a synchronised channel that passes a message is planned.
DeclarationKindDirection
Chan c = a --> b;signallinga to b
Chan c = a <-> b;signallingboth ways; see WF2
Sync Chan c = a --> b;signallinga to b, a of lower priority
Chan c = a --> b via region<T>;message passinga to b, values of T

The Async keyword may be omitted — a Chan without a leading Sync is asynchronous. The arrow is always written: Sync channels and buffered channels take --> only. The trailing semicolon is optional.

Fields

  • Name — snake_case identifier. The same name appears in process expressions on the LHS of ? / !.
  • Endpoints — two distinct protection-domain names. Both must be declared in the same .fis file. A Sync channel’s sender must have a strictly lower priority than its receiver (seL4 protected procedure calls run low to high).
  • Buffer (optional, after via; --> channels only) — the MemoryRegion that holds the channel’s values and the type of a value: via packet_buffer_outer<int>, a declared data-layer struct (via eth_outer_output<Slot>), or raw bytes, via ring<byte>. The type is a struct or a scalar, never an array, and has at least one byte; it is the value the channel carries, Σ(c). A struct is the channel’s communication type, and the C backend types receive binders from it (o2d?pkt declares static struct Slot pkt;). via on a <-> or Sync channel is a parse error.

Signalling channels

A signalling channel is a Microkit notification: a pure synchronisation point. c! notifies the other end; c? is enabled when the PD was notified on c. Notifications do not queue: several sends before the receiver runs wake it once.

A Sync channel is declared synchronous: the sender calls the receiver, as a protected procedure call from the lower-priority PD to the higher, and the receiver’s end is marked pp in the SDF. The C backend sends it as a notification today; the call, and carrying a value with it, are #602.

Examples

// Signalling, one way.
Chan tick = timer --> worker;

// Signalling, both ways — `Async` is the default, can be omitted.
Chan d2i = dd <-> eth_inner;
Async Chan s2o = simulate <-> eth_outer;

// Signalling, synchronous: the lower-priority eth_outer calls dd.
Sync Chan call = eth_outer --> dd;

// Message passing: buffered, a value of a declared struct.
Chan o2d = eth_outer --> dd via eth_outer_output<Slot>;

// Message passing: buffered, raw bytes.
Chan ring = eth_outer --> eth_inner via ring_buffer_outer<byte>;

Buffered channels

A channel declared Chan c = a --> b via region<T>; is a FIFO queue of T values from a to b, held in region as a ring: Lamport’s single-producer single-consumer queue, which needs no lock because each index has one writer (the sender moves the tail, the receiver the head).

  • Layout. A 16-byte header holding the two indices and a signal word, then N slots of T, packed. N is the channel’s capacity: via r<T, N> declares it (a literal or a const), and it must be at least 1 and fit in the region after the header, else an error at the channel; without it, N is as many as fit, ⌊(size − 16) / sizeof(T)⌋, or 2³¹ − 1 if that is smaller (the indices’ bound), with a warning that the rest of the region is unused.
  • Order. Values are received in the order they were sent, each once.
  • Send, c!e. Copies the value of e into the next slot, and notifies the receiver if the receiver asked. A send to a full ring is lost: the sender goes on and no notification is sent.
  • Receive, c?x. Copies the oldest value into x. A receive waits while the ring is empty, and is enabled whenever the ring holds a value, whatever notification woke the PD, so a receiver drains everything that is queued. A receive that finds the ring empty asks to be notified (sDDF’s signalling protocol), so a receiver that is still draining costs the sender no system call.
  • By copy. Values cross by copy, in both directions; neither PD holds a reference into the region.
  • The region. It is mapped into both endpoint PDs by fic (rw, cached, at addresses fic chooses): it must not also appear in a Mapping, and it backs one channel only. Only fic’s runtime reaches it: the generated unit exports no symbol for the region.

Synchronised channels

Planned, not yet in the language: a Sync channel that passes a message, the value carried in the protected procedure call itself, by copy (#602).

Channel events in process bodies

Inside a process, channel events are written chan_name '?' ident (receive) and chan_name '!' expr (send) on a message-passing channel, and chan_name '?' and chan_name '!' on a signalling one. The names must match exactly; typing resolves each event back to the declared ChannelDecl and checks that the PD is one of its endpoints, that it may send or receive there (either end may do both on a <-> channel), and that the value matches the payload type.

Channel events are the only way to a channel. Imported C or Pancake cannot call the ring behind a buffered channel: in a .c import the ring is not yet declared, and a separate driver or Pancake object that calls it fails to link.

See Event Declarations → Channel events for the inline event grammar and Process Definitions for how channel events sit in a process expression.

WF2 and bidirectional channels

fic requires the channel dependency graph to be acyclic (WF2): a PD that receives from another waits for it, and a cycle is a circular wait. A bidirectional channel adds the edge in both directions, so every <-> channel fails the check unless --allow-wf2-cycles is given (or allow_wf2_cycles = true in fire.toml), which defers deadlock-freedom to an external authority such as fire verify. The demos pingpong and pingpongpan use <-> this way. See Well-Formedness for the check and its error.

Limitations

  • The Sync modifier rejects bidirectional <-> syntactically; sync bidirectional channels would require a richer call/reply protocol than the current implementation supports.

Imports and Mappings

Two declarations sit at the top of every .fi file: import brings an external C or Pancake source file into scope under a chosen alias, and Mapping puts a memory region declared in the .fis into the protection domain’s address space.

Imports

ImportDecl ::= 'import' '"' FilePath '"' 'as' ident ';'
FilePath   ::= any text up to the closing quote   -- one line, relative to the project

An import declaration names the external implementation that backs the PD’s computation events. The parser takes the path as written, up to the closing quote, and decides nothing about it; the front end reads it relative to the project directory (import "include/eth.h" as eth; is valid) and picks the reader from the extension: .c and .h are C, .pnk is Pancake. Any other extension is rejected when the project loads. Every alias.f(..) call then resolves to a function the file exports, or the build fails. The alias becomes the prefix on every external call inside the PD.

What counts as exported depends on the language. For C, fic reads the file with libclang: every function that is neither static nor inline. For Pancake it scans the source for export fun declarations, which take at most four word arguments and return one word; their /@ ... @/ contract blocks are read alongside.

import "include/eth.h" as eth;     // C header; src/eth.c is linked
import "pingpong.pnk" as io;       // Pancake source — same call shape

Multiple imports are allowed, and they may interleave with mappings — order does not matter for parsing. Each alias must be unique within the file.

Mappings

MappingDecl ::= SecurityLabel? 'Mapping' ident '(' region (',' vaddr)? ',' perms (',' cached)? ')' ';'

region      ::= ident                      -- a MemoryRegion declared in .fis
vaddr       ::= hex                        -- explicit virtual address (optional)
perms       ::= string_literal             -- 'r', 'rw', 'rx', 'rwx', 'x', 'wx'
cached      ::= bool_literal               -- default: true

A mapping declaration installs a MemoryRegion into the PD’s address space. The mapping’s name derives the auto-emitted setvar symbols (<mapping>_vaddr, _paddr, _size) patched into the PD’s ELF — see Boot Initialisation.

Fields

  • Security label — High or Low prefix, default Low. A mapping’s label must be at least its region’s: a Low mapping of a High region is rejected. See Information-flow labels below.
  • Name — the mapping’s own identifier. Distinct from the region’s name; one region can have multiple mappings under different names.
  • Region — the MemoryRegion declared in the .fis file.
  • Vaddr (optional) — pin the mapping at a specific virtual address. If omitted, the loader allocates one. Hex literal.
  • Permissions — a quoted string of r/w/x characters. Order and case are insensitive: "rw" and "WR" are equivalent. Write-only is rejected; at least r or x must be present. The accepted set is r, rw, rx, rwx, x, wx.
  • Cached (optional, default true) — whether the mapping is cached in the CPU MMU. Device MMIO regions should be set false explicitly.

Examples

// Anonymous shared buffer at allocator-chosen vaddr, read-write, uncached.
Low Mapping ring_buffer(ring_buffer_outer, "rw", false);

// Same region, default cached flag (true).
Mapping packet_buffer(packet_buffer_outer, "rw");

// Pinned vaddr — useful for debugging or for binding two PDs to a
// shared layout that pre-allocates virtual addresses.
Low Mapping eth0(eth0, 0x2_000_000, "rw");

// High-side mapping of a High MemoryRegion. A Low mapping of that region
// would be rejected.
High Mapping eth_clk(eth_clk, 0x2_200_000, "rw");

// Read-only mapping (data-diode input).
Low Mapping input_buf(eth_outer_output, "r");

Information-flow labels

Both MemoryRegion and Mapping declarations may carry a High or Low prefix. The two-level lattice is:

flows_to(Low,  Low)  = true
flows_to(Low,  High) = true       // upgrade is fine
flows_to(High, Low)  = false      // downgrade is rejected
flows_to(High, High) = true

In source: Low is the default — omitting the prefix is equivalent to writing Low. Place the prefix before the MemoryRegion / Mapping keyword; placing it elsewhere is a parse error.

This is the one information-flow rule: the information-flow check, run after typing, rejects any mapping that violates flows_to(region.label, mapping.label), so a High region is never read through a Low mapping. Protection domains carry no labels of their own. The data-diode demo uses this to enforce one-way information flow. The Information Flow chapter has the detail, and the Memory Region Declarations chapter states the same rule from the region’s side.

A mapping’s addresses

A mapping is a value only through its addresses:

  • m.vaddr is its virtual address, which fic chose (or you pinned). It compiles to that constant.
  • m.paddr is the physical address of its region. It may be known only when the system boots, so it compiles to the symbol m_paddr, which the loader patches. fic declares and patches m_paddr only in a PD that reads it. On Microkit, a region whose paddr is read must be physically contiguous; Microkit picks its address when the region declares none, and on x86-64 the region must declare one.

Validation

  • Each Mapping’s region must reference a declared MemoryRegion.
  • Permission strings must contain at least one of r or x. "w" alone is rejected.
  • A pinned vaddr must be aligned to the region’s page size.
  • Mapping names are unique within the same .fi file.

Boot Initialisation: the microkit.init Process and Auto-Setvars

Boot-time behaviour of a protection domain is expressed in two ways:

  1. Address binding is automatic: every Mapping exports its addresses to the imported C / Pancake implementation through a naming convention (the setvar mechanism below). No syntax is required.
  2. Boot-time logic is modelled by an ordinary process bound to the platform’s boot entry point with @bind(microkit.init) — the model-level counterpart of Microkit’s void init(void) entrypoint, which the imported source file implements.

The boot process

The boot process is the one annotated @bind(microkit.init). Its name carries no meaning — Init is a common choice, but the binding, not the name, is what makes it the boot entry point:

@bind(microkit.init)
proc Init() {
    setup_eth -> Skip;
}

Microkit calls the PD’s entrypoint exactly once, before any event is delivered, so the bound process must not contain channel receives or IRQ awaits. When it terminates (Skip), control falls through to the @bind(microkit.notified) event loop — exactly as the generated C init() runs the boot body and then arms notified().

A @bind(microkit.init) process is mandatory for every PD that has a .fi program when targeting Microkit (--emit=c or image generation): the kernel calls init() on every PD at startup. It is mandatory in tandem with @bind(microkit.notified) — Microkit invokes both, so a conforming PD binds both (any other platform entry points are optional). A PD with no boot work still declares a no-op:

@bind(microkit.init)
proc Init() { Skip; }

The @bind(microkit.notified) process, in turn, must be receive-headed if it receives at all; see Annotations. Both are checked in every mode, --emit=xta included; see Entry Points.

Auto-emitted setvars

For every mapping named m, the compiler emits setvar candidates for three ELF symbols:

SymbolPatched with
m_vaddrVirtual address where the mapping was installed.
m_paddrPhysical address of the backing region. Always linked: if the region was declared without an explicit phys_addr, the kernel fills it at boot.
m_sizeRegion size in bytes.

Before image generation (--emit=img), candidates whose symbol is not declared in the PD’s compiled ELF are dropped — the implementation only receives the symbols it declares. The Microkit loader patches the surviving symbols before the PD starts.

import "include/eth.h" as eth;

Low Mapping ring_buffer(ring_buffer_outer, "rw");
Low Mapping packet_buffer(packet_buffer_outer, "rw");

/* src/eth.c — declared symbols are patched by the loader */
uintptr_t ring_buffer_vaddr;    /* ← ring_buffer.vaddr  */
uintptr_t ring_buffer_paddr;    /* ← ring_buffer.paddr  */
uintptr_t packet_buffer_vaddr;  /* ← packet_buffer.vaddr */
/* packet_buffer_size not declared → no setvar emitted   */

Pick mapping names so that <mapping>_vaddr matches the symbol your implementation uses.

Derived values

setvar only supports literal-substitution patching: it cannot evaluate arithmetic. Values derived from a mapping address (for example, an offset into a ring buffer) are computed at runtime inside the implementation’s init function.

Validation

  • Mapping names must be unique within a PD (checked by name resolution); this also guarantees the derived setvar symbols are unique.
  • m_paddr is always linked: when the underlying MemoryRegion has an explicit physical address that value is patched in, otherwise the kernel assigns one at boot.

Variable Declarations

VarDecl ::= ident ':' Type ';'
Type    ::= BaseType ('[' ArrayLen ']')?
BaseType ::= PrimitiveType | StructName

A variable declaration introduces one named value at PD-global scope or inside an event body. The ident: Type; form is the only shape supported today; an initialiser (ident: Type = expr;) is reserved but not yet parsed.

🚧 Initialiser syntax (= expr) is reserved but unparsed — see #105. For now, initialise locals from inside the body, and globals from the imported source’s init() function (see Boot Initialisation).

Scopes

Variables can appear in three positions inside a .fi file:

  • Global — at the top level of the file, alongside Mapping and import declarations. Globals are visible everywhere in the PD, read/write inside event bodies.
  • Event local — inside a computation event body, from its declaration to the end of the event body (the statement’s ;, or the closing }).
  • Process variable — inside a process body: a parameter (proc Drain(pkt: Slot), read-only, in scope for the whole body), a declaration x: T; (in scope for the rest of its sequence), or a receive binder c?x on a buffered channel (in scope for the rest of its prefix).

A name in a body is looked up among that body’s own variables first, then the program’s globals, then the system’s constants:

body variable → global → constant

Event and process variables never see each other: a process value reaches an event only as a carrier. Shadowing a global, a mapping or a constant is a warning; declaring a name twice in one body while the first is still in scope is an error. Carriers are read-only — see Event Declarations.

Primitive types

The primitive types accepted in declarations are:

GroupTokens
Signed integersint, int8, int16, int32, int64
Unsigned integersuint, uint8, uint16, uint32, uint64
Booleanbool
Byte aliasbyte (8-bit)
AddressAddress

int and uint are aliases of int64 and uint64 on every target. byte is an alias for uint8. There is no void type — every declared variable has a concrete, storable type; void is a reserved word, so v: void; is a parse error.

Struct types and arrays

pkt: Slot           // user-defined struct — declared in the .fis data layer
buf: uint8[16]       // fixed-size array — length is a literal or const name

Any identifier that isn’t a recognised primitive keyword is treated as a struct type name, resolved against the .fis struct declarations during name resolution (unknown names are rejected there, not at parse time). Fiducia has no pointer types — there is no ptr<T> syntax.

Examples

// Global declarations, top of a .fi file.
counter: int;
ready: bool;
last_irq_ts: uint64;

// Local declarations inside an event body.
evt handle_packet.|size: int|: {
    local_buf: uint8[64];     // local
    ok: bool;                 // local
    local_buf = eth.alloc();  // assignment uses globals/locals/carriers
}

Validation

  • A variable name is unique within its enclosing scope (multiple globals with the same name are rejected; a body variable may shadow a global, with a warning).
  • The type must be a recognised primitive, Address, a fixed-size array of one, or a struct name that resolves to a real .fis struct declaration.

Event Declarations

EventDecl   ::= 'evt' ident Carriers? ':' Body
Body        ::= Statement | '{' Statement* '}'
Carriers    ::= ('.' '|' Param (',' Param)* '|')+
Param       ::= ident ':' Type

An event declaration introduces one named atom of computation at the top level of a .fi file using the evt keyword. Processes reference it by name on the left of a prefix (my_event -> ...).

evt declarations and proc definitions may appear in any order in a .fi file: a process can use an event declared below it.

Computation events are one of three event kinds in CoreFi (paper §4.2); the other two — channel events (c?x / c!e, or c? / c!) and hardware-interrupt events (irq?N / irq!N) — are inline atoms that appear in process bodies and have no top-level declaration.

Computation events

A computation event is a named, atomic block of statements: assignments and external calls, plus optional carrier parameters. The block executes as a single transition in the labelled-transition system — processes can prefix on it (my_event -> ...) but cannot observe it mid-flight.

Names follow snake_case and start with a lowercase letter. This both signals intent and lets the parser disambiguate between a computation event reference and a sub-process reference (which uses UpperCamelCase).

Body

After the :, the body is either one statement (a local variable declaration, an assignment, an external function call or debug output), ending at its ;, or any number of statements in braces. Either way the body ends where it says, so what follows it is never read as part of it: a global declared below an event stays a global.

// One statement: no braces, ends at its ;
evt setup_eth: eth.eth_setup();

// Several statements: braces.
evt handle_packet.|size: int|: {
    local_buf: int;
    local_buf = eth.alloc(size);
    counter = counter + 1;
}

Debug output

A dbg(...) statement prints values from an event body; see Debug Output.

Carriers

evt handle_packet.|size: int|:                  // single carrier
evt ack.|chan: int, slot: int|:                 // grouped carriers
evt ack.|chan: int|.|slot: int|:                // chained carriers (equivalent)

Carriers are parameters supplied by the invoking process. The syntax uses pipes (.|...|) — chosen over parentheses so the visual boundary is distinct from sub-process parameter lists. Multiple carriers may be grouped in a single .|x: int, y: int| clause or chained across multiple .|x: int|.|y: int| clauses; both forms behave identically.

Inside the body, carriers are read like any other variable: passed to external calls (eth.handle_rx(idx)) or read in expressions (local_buf = eth.alloc(size)). They are read-only; assigning one is an error. Three kinds of variable names can appear in an event body:

KindDeclared inWritable
GlobalTop-level of the .fi fileyes
CarrierThe event’s `.name: type
LocalInside the body via name: Type;yes

An event sees its own locals and carriers, then the program’s globals and the system’s constants, never a process variable; lookup and shadowing are in Scopes. To carry mutable state across event invocations, use a global; to carry mutable scratch within one invocation, declare a local variable.

Referencing an event

EventRef ::= ident ('.' ident)*

A process runs an event by naming it, followed by one .ident per carrier, written without whitespace around the dots. The identifiers are the process’s own variables (a parameter, a receive binder, a declaration or a global), supplied in the order the event declares its carriers:

evt forward.|pkt: Slot|: { ... }
evt ack.|chan: int, slot: int|: eth.ack_slot(chan, slot);

proc Relay(pkt: Slot, c: int, s: int) {
    forward.pkt -> ack.c.s -> Skip;
}

Examples

// No carriers — the event is a fixed call.
evt setup_eth: eth.eth_setup();

// Single carrier, single-statement body — idx is the carrier.
evt read_frame.|idx: int|: eth.handle_rx(idx);

// Several statements, in braces — size carrier passed to alloc.
evt handle_packet.|size: int|: {
    local_buf: int;
    local_buf = eth.alloc(size);
    counter = counter + 1;
}

// Multiple carriers, grouped form.
evt ack.|chan: int, slot: int|: eth.ack_slot(chan, slot);

// Same event, chained carrier form (equivalent).
evt ack.|chan: int|.|slot: int|: eth.ack_slot(chan, slot);

Empty-body events

evt noop: {} is an event with no statements. Useful as a placeholder while a process expression is being prototyped.

Channel events

ChannelEvent ::= ident '?' ident?            // c?x / c? — receive
              |  ident '!' Expr?             // c!e / c! — send

A channel event is an atomic communication action between two protection domains. The channel name on the LHS is resolved against the Chan declarations in the surrounding .fis.

Channel events appear inline inside process expressions — they have no top-level declaration.

A message-passing channel carries a value; today that is a buffered channel (via r<T>), whose type T is the value’s. On it the receive form c?x binds the incoming value to x for the rest of that prefix only (c?x -> P): the binder is gone at the next ;, and a referenced process does not see it unless it is passed as an argument (c?x -> Drain(x)). The send form c!e transmits the expression e, of type T. A signalling channel is a Microkit notification, which carries no value: its events are c? and c!, and a value or binder on it is an error (channel 'ball' has no buffer, so it carries no value), as is leaving one off a buffered channel.

No selective receive

The RHS of ? is always a single identifier (a binder), never a value pattern. Traditional CSP / CSP# accepts c?ACK as “wait only for the message ACK”, but Fiducia rejects this: it can deadlock when no sender ever produces the matching value, conflicting with CoreFi’s deadlock- freedom story (paper §4.1 Wf1). The same expressiveness is recovered by binding then guarding:

// Recommended.
c?msg -> [msg == ACK] handle_ack -> Skip [] [msg == NACK] handle_nack -> Skip

Send-payload style

The RHS of ! accepts any Expr — the parser does not reject a call expression there today. The recommended style is still to keep channel events as pure-communication atoms: bind a call’s result in a computation event first, then send the bound variable, rather than calling directly in send position. This keeps side-effecting work legible as its own step in the process algebra, even though the grammar itself doesn’t enforce it:

// Discouraged (parses, but buries a side-effecting call in a
// communication event):
// c!eth.get_packet()

// Recommended: bind, then send (pkt is a global variable).
evt get_pkt: pkt = eth.get_packet();
proc P() { get_pkt -> c!pkt -> ... }

Hardware-interrupt events

IRQEvent ::= 'irq' '?' integer_literal       // irq?N — await
          |  'irq' '!' integer_literal       // irq!N — acknowledge

A hardware-interrupt event is a special-cased channel event on the reserved channel name irq. The integer is the IRQ number declared on the protection domain. irq?N blocks until the IRQ fires; irq!N acknowledges the IRQ back to the kernel. The literal is not checked against the IRQ the protection domain declares: a mismatch is not reported.

Like channel events, IRQ events appear only inside process expressions and have no top-level declaration:

proc Notified() { irq?159 -> Handle_eth(); irq!159 -> Notified(); }

🚧 self.IRQ syntax is planned (#164) — irq?self.IRQ / irq!self.IRQ will resolve the protection domain’s IRQ number without a magic literal.

Debug Output

Dbg    ::= 'dbg' '(' (DbgArg (',' DbgArg)*)? ')' ';'
DbgArg ::= text_literal | Expr

dbg prints its arguments in order, then a newline. A text literal is printable ASCII between double quotes, with the escapes \\, \", \n and \t. Any other argument is an expression of an integer type, or a bool, which prints as true or false.

evt tally: {
    dbg("round ", rounds);
    rounds = io.tally(rounds);
}

dbg is a statement, so it is valid only in an event body: not in a proc body, a guard or an expression. It is for debugging only. The model leaves it out, so no argument may call a function: removing the dbg must not change what the event does. Put a dbg in an event that does other work, as above. An event that only prints does nothing in the model, and fic warns about it when it emits the model.

Each line starts with the name of the protection domain that printed it, then : , so dbg("round ", rounds); in ping prints ping: round 3. An integer prints in decimal at its full width, a signed one with its sign: -1 prints -1, and every uint64 prints in full; a bool prints true or false. fic’s runtime, filib, which every protection domain links, writes each byte as it comes, so lines from protection domains running at once can interleave on the shared console.

All output is the .fi’s. By convention, imported C and Pancake use neither Microkit nor seL4 directly: no microkit.h or sel4/… include, no microkit_… or seL4_… call, no @microkit_… FFI, in the import or in the C linked beside it (a header’s source, a Pancake file’s FFI shims). A channel operation or a print there would be invisible to the model, so what fire verify proves would not be about the system that runs. fic does not check this yet.

Process Definitions

ProcessDecl ::= Bind? 'proc' UIdent '(' (Param (',' Param)*)? ')' '{' ProcessBody '}'
Bind        ::= '@bind' '(' ident '.' ident (',' ident '.' ident)* ')'
Param       ::= ident ':' Type

ProcessBody ::= BodyItem (';' BodyItem)* ';'?
BodyItem    ::= VarDecl | ProcessExpr
VarDecl     ::= ident ':' Type ';'
ProcessExpr ::= 'Skip'
             |  'Div'
             |  Event '->' ProcessExpr
             |  '[' Guard ']' ProcessExpr
             |  ProcessExpr ('[]' ProcessExpr)+ ('default' ProcessExpr)?
             |  ProcessRef
             |  '(' ProcessExpr (';' ProcessExpr)* ';'? ')'
ProcessRef  ::= UIdent '(' (ident (',' ident)*)? ')'
Guard       ::= Expr   -- boolean-shaped: comparison, &&/||/!, boolean
                        -- variable/call/field access; not arithmetic

A process definition is the orchestration layer of a Fiducia protection domain — a CSP-style algebraic expression composed from events, guards, choices, and sequential composition. Each proc declaration introduces one named process; all proc declarations in the same .fi file are mutually visible and may reference each other by name.

proc definitions and evt declarations may appear in any order in the file.

Following CoreFi paper §4.2, a process expression is one of:

FormNotationMeaning

DivergenceDivDivergence (a self-loop, Ω).
Event prefixe -> PPerforms event e, then P.

Default arm(P [] Q) default RR runs when no branch is enabled.
SequentialP ; QP to completion, then Q.

Naming convention

Process names use UpperCamelCase. This both signals intent and disambiguates process references from computation event references at parse time:

  • Reply(pkt) — sub-process call (UpperCamelCase, parentheses required).
  • send_frame.pkt — computation-event reference (snake_case, dot carrier syntax).

The disambiguation happens on the leading character of the identifier. The boot process is the one bound with @bind(microkit.init); Init is a conventional name but carries no special meaning (see Boot Initialisation).

Annotations (@bind)

A process may carry a single @bind(...) annotation mapping it to one or more platform entry points, without hardcoding kernel terminology into process names. Group the targets — one platform.entry pair per platform — on one line:

@bind(microkit.notified, cheri.interrupt_handler)
proc Notified() { o2d?pkt -> d2i!pkt -> Notified(); }
  • A process with no @bind is internal — not directly callable by the kernel.
  • @bind is authoritative for entry-point selection. The C backend and the UPPAAL lowering pick kernel entry points by binding, not by process name: the microkit.init-bound process becomes init() (the boot body) and the microkit.notified-bound process becomes the notified() event loop.
  • The process bound to microkit.notified, if it receives at all, must be receive-headed: every path at its head, through [], the left of ; and a helper’s body, begins with a receive (c?x) or an IRQ await (irq?N), with no guard and no default at the top (a receive on a buffered channel may be guarded: its values wait in the ring). The kernel invokes it for a message, which the head consumes; a handler that could run without one would never return to the kernel. See Well-Formedness.
  • Both a @bind(microkit.init) and a @bind(microkit.notified) process are mandatory for every PD with a program when targeting Microkit — Microkit invokes both on every PD, and the front end reports a PD that lacks one whatever the output (--check, --emit=xta, --emit=c, an image). See Boot Initialisation and Entry Points. Other platform entry points are optional.
  • Each entry point binds at most one process. Two processes both @bind(microkit.notified) is an error — resolution rejects the second rather than silently keeping the first.

Choice and discriminators

Every branch of a [] choice must carry a discriminator — a distinguishing prefix that the surrounding environment can pattern-match on. The parser checks structurally and recurses into a branch’s first sequential item and into nested choices; deferred resolution is required only for ProcessRef (the validator follows the name).

Common discriminator shapes:

e -> P()                // event prefix
[b] P()                 // guard
c?x -> ...              // channel-event prefix

A branch that is bare Skip, Div or a variable declaration is a parse error: it is always enabled, so it discriminates nothing. A branch that is a sequence is judged by its first item.

The optional default arm is taken when no branch’s guard succeeds. It needs no discriminator of its own. A branch that begins with a receive on a buffered channel fires beside it when the ring holds a value, so the default runs only on an empty ring; a signal receive or IRQ await beside a default is a branch with no guard (see Well-Formedness).

// d buffered: take a value if there is one, else go on.
d?v -> Use(v) default Skip;

Examples

// Two branches, no default.
proc Dispatch() {
    [rx] receive -> Skip [] [!rx] cleanup -> Skip;
}

// Two branches with a fallback.
proc Reply(pkt: int) {
    [pass]  o2d!pkt -> Skip
 [] [!pass] handle_ping -> Skip
    default Skip;
}

Guards

Guard ::= Expr   -- boolean-shaped: comparison, &&, ||, !, a boolean
                 -- variable, call or field access; not arithmetic

A guard gates the next process expression on a boolean expression: [rounds < 3], [!ready], [io.keep_playing(rounds) != 0]. A guard whose top node is arithmetic ([a + b]), an integer literal or sizeof is rejected; arithmetic inside a comparison ([a + b == c]) is fine. The guard binds tighter than []:

[b] e -> P [] e2 -> Q   ≡   ([b] (e -> P)) [] (e2 -> Q)

The guard applies only to the first branch.

Recursion

A process refers to itself, or to another process, only in tail position: as the last thing it does, so the reference is a jump back to that process’s head and the control graph stays finite. A reference followed by more work is rejected:

proc Notified() { ball? -> Notified(); tally -> Skip; }   // error: non-tail
proc Notified() { ball? -> tally -> Notified(); }         // ok

This holds for the entry process too: Notified() at the end of Notified loops back to its head within the invocation. Only reaching the end (Skip) returns to the kernel, and the next notification invokes notified again. A loop whose head receives waits there for the next message; one that never receives never returns (Skip; Notified() on a PD’s own CPU budget).

Inside a non-final operand of ;, no enclosing process may be referenced: its continuation would need a return stack. See Well-Formedness.

Sequential composition

Inside a {} body, ; separates items. The last item may carry a trailing ; before }:

proc Notified() {
    irq?159 -> Handle_eth();
    irq!159 -> Notified();
}

Sub-process calls

ProcessRef ::= UIdent '(' (ident (',' ident)*)? ')'

A sub-process call references another process declared in the same file. The argument list is currently restricted to identifiers. Parentheses are always required — even for empty argument lists (Skip and Div are the only bare uppercase atoms):

proc Notified()   { irq?159 -> Handle_eth(); irq!159 -> Notified(); }
proc Handle_eth() { handle_irq -> Dispatch(); }
proc Dispatch()   { [rx] receive -> Skip [] [!rx] cleanup -> Skip; }
proc Reply(pkt: int) { o2d!pkt -> Skip; }

The validator confirms each ProcessRef resolves to a declared process and that the argument count matches.

Empty processes

Skip and Div are atomic and self-contained: Skip is successful termination, Div is divergence (a self-loop):

proc NoOp()  { Skip; }
proc Stuck() { Div; }

Limitations

  • Argument lists for ProcessRef and computation-event references are restricted to identifiers. Channel-receive RHS accepts identifiers or integer literals (so irq?159 parses).
  • Currently only variable declarations (x: int;) are permitted as inline body items alongside process expressions. Assignment statements and external calls must live in evt declarations. This restriction is planned to be lifted: future versions will allow statements directly in proc bodies, with flexible interleaving of statements and process expressions.
  • Recursion is modeled as a sub-process call by name, in tail position only (see Recursion).
  • A receive binder does not reach a referenced process: pass it as an argument, c?x -> Drain(x) with proc Drain(x: T) (see Scopes). An entry point (@bind) takes no parameters.

Expressions

This chapter describes the expression grammar fic actually parses. Expressions appear as:

  • the right-hand side of assignments inside event bodies;
  • the payload of a channel send (c!e);
  • the body of a guard ([b]);
  • arguments to calls, sub-process calls, and computation-event carriers.

One grammar (Expr) covers literals, variables, calls, sizeof, unary and binary operators, field access, and casts. There’s no separate arithmetic vs. logical vs. boolean sub-grammar — a boolean-shaped subset of Expr is what’s required in guard position (see below), not a different grammar.

Expr    ::= Lit | ident | CExpr | 'sizeof' '(' Type ')'
          | UnOp Expr | Expr BinOp Expr
          | FieldBase '.' ident           -- field access
          | Expr 'as' Type                -- cast
FieldBase ::= ident | CExpr | FieldBase '.' ident  -- var, call, or field chain

Lit     ::= int_lit | hex_lit | bool_lit
                                        -- hex_lit allows '_' (0xFE00_0000); int_lit does not
UnOp    ::= '-' | '!' | '~'
BinOp   ::= '+' | '-' | '*' | '/' | '%'
          | '==' | '!=' | '<' | '<=' | '>' | '>='
          | '&&' | '||'
          | '&' | '|' | '^' | '<<' | '>>'

Names, mappings and fields

A variable is a program or body variable or a system const. A mapping is not a value: m alone is an error, and only m.vaddr and m.paddr are expressions, the two addresses of a mapping. Any other x.f is field access on a struct value (a variable, a call, or a chain of fields).

A constant subexpression is folded at compile time in the checked arithmetic of its type; a constant that overflows is a compile error, not a wrapped value.

Casts

e as T converts an integer or an address to another integer type or to Address, explicitly: fic never widens or narrows on its own, so m.vaddr + w with w: uint32 is an error and m.vaddr + w as uint is the way to write it. The semantics are Rust’s: widening is lossless, narrowing is modulo 2ⁿ (300 as uint8 is 44, 200 as uint8 as int8 is -56), and a constant cast folds at compile time. as binds tighter than every binary operator and looser than unary: -x as uint is (-x) as uint. A cast to bool, to a struct or to an array is rejected, as is a cast of one.

Call expressions (CExpr)

CExpr ::= ident '.' ident '(' (Expr (',' Expr)*)? ')'

A call expression invokes a function defined in an imported .c file, prefixed with the import alias chosen at the import declaration. The alias is required — there are no local callables in Fiducia, only externally-implemented functions reached through an alias.

The first ident is the alias; the second is the function name. No whitespace is permitted around the . or before the (:

eth.send_frame()                  // OK
eth.send_frame(pkt, len)          // OK — arguments are full Expr, comma-separated
drv .start()                      // rejected — whitespace before '.'
drv. start()                      // rejected — whitespace after '.'
drv.start ()                      // rejected — whitespace before '('

Guard expressions

A guard ([b] P) requires a boolean-shaped Expr — arithmetic like [a + b] is rejected at parse time, since a guard must denote a yes/no decision, not a value. Boolean-shaped means: a boolean literal, a variable, a call, a field access, a !-negated boolean-shaped expression, or a comparison/&&/|| combination of boolean-shaped expressions.

[a + b == c]              // OK — comparison of arithmetic is boolean-shaped
[eth.is_forward()]         // OK — call
[!flag && ready]           // OK — negation + conjunction
[true]                     // OK
[a + b]                    // rejected — arithmetic isn't boolean-shaped

A call in a guard must be side-effect free, because the generated C may evaluate a guard more than once. For a Pancake function with a contract, fic --check and --emit=xta reject a call whose contract is impure.

Entry Points

A protection domain does nothing until the platform calls it. The handlers the platform calls are the PD’s entry points, and a proc becomes one with a @bind annotation:

@bind(microkit.init)
proc Init() { ball! -> Skip; }

@bind(microkit.notified)
proc Notified() {
    ball? -> tally -> Skip;
    [io.keep_playing(rounds) != 0] ball! -> Notified()
 default Skip;
}

@bind(<platform>.<entry>) is platform-neutral: the parser records the pairs on the process and decides nothing about them. The entry points a platform has, and what each means, belong to that platform. A process with no @bind is internal: it runs only when a bound process references it.

Microkit

Microkit is the platform fic targets, and it has two entry points:

EntryMicrokit’sRuns
microkit.initinit()once, when the PD boots. See Boot Initialisation.
microkit.notifiednotified(channel)each time the kernel notifies the PD, for a channel message or an interrupt.

Both are mandatory. Every protection domain binds both, and the front end reports one that does not, naming the PD and the missing entry, before any backend runs: fic --check, --emit=xta and --emit=c all stop. Each entry point binds at most one process.

A notified process that receives must be receive-headed: it starts by consuming the message or interrupt that woke it (see Process Definitions). The generated C makes each receive or interrupt await in the process a resume point that notified() dispatches to, and init() runs the boot process.

A microkit. name other than init and notified is accepted by the grammar and ignored.

Other platforms

A process may name several platforms on one line, @bind(microkit.notified, cheri.interrupt_handler). fic compiles the microkit pairs; the others are kept and not used.

Foreign Functions

A program reaches code written in another language through an import: import "pingpong.c" as io; makes every function the file exports callable as io.f(..) from an event body or a guard. This chapter says what an import exposes, how a foreign signature becomes a Fiducia one, and where each failure is reported. Contracts covers the annotations a function may carry.

What a file exports

fic reads the imported file itself; it does not run the foreign compiler to find out what the file offers.

The language is the extension’s: any other extension is rejected when the project loads (import "x.rs": not a C or Pancake file), and so is a file that cannot be read. A .c import is compiled into the protection domain’s unit; a .h import is a driver whose .c is found beside it, or in src/ for a header under include/ (include/eth.h is backed by src/eth.c), and is linked; a .pnk import is compiled by CakeML into the image. Every other .c in the project, outside build/, is compiled into one archive, build/libproject.a, linked after each PD’s objects: the linker takes only the files that define something still missing, so a driver reaches the C it calls (eth.c calls util.c) without the .fi importing it, and a file nothing calls is left out. If two files define the same function, the linker takes the first it needs, without an error.

A protection domain has no C library. Its C may call memcpy, memmove, memset, memcmp and bcmp, which fic’s runtime supplies; anything else it calls, it brings.

Calls

A call alias.f(args) is typed against the lowered signature: the argument count and types must match, and a result is used at its own type (an int32_t result is not an int; convert it with as). Failures:

  • Unknown function. io.nothing(1) and a static function alike are foreign function 'io.hidden' is not declared, reported where the call is.
  • Wrong arity. 'twice' takes 1 argument(s), found 2.
  • Type mismatch. expected 'int64', found 'int32'.

A struct passed or returned is the .fis struct of that name, whose layout both sides share.

When each failure is reported

An unreadable file or an unsupported extension is reported when the project loads, at the import. An unknown function, a wrong argument count or type, and a signature with no Fiducia type are reported at the call. An annotation outside the contract subset, or a call the contract cannot support, is reported by --check and --emit=xta, which read the contracts. The foreign compiler’s own errors surface only when an image is built.

Contracts

A foreign function may carry a contract: requires and ensures clauses written in the function’s own language. A contract does two jobs, and only one of them is fic’s.

  • The model assumes it. --emit=xta turns a contracted function that a protection domain calls into a UPPAAL function ffi_<name>: each requires is an assert at every call (never a guard), and the deterministic ensures is the value the call returns.
  • A verifier proves it against the code: Frama-C with -wp for C, pancake2viper for Pancake. fire verify runs them; see the fire verify chapter of the manual for the tools and their setup.

So the model is only as sound as the contracts, and fic never derives a clause itself: it translates what the annotation states.

Anything outside the subset is rejected by its name, so a contract never seems read when it was not:

error: cq/ping.fi: ACSL contract error in "pingpong.c": function `tally`:

Clauses the subset does not cover at all are the verifier’s and are not an error: in ACSL named behaviours, assumes, terminates and exits, and in Pancake any annotation other than requires and ensures (a trusted, an invariant).

What the model needs of a call

For a Pancake function the model checks each call site, because it must produce a value the automaton can use:

  • A call whose value is used, rather than made as a bare statement, needs a deterministic ensures retval == E. Without one, --check reports that the function has “no deterministic ensures retval == ... clause”.
  • A call in a guard must also be pure, because the generated C may evaluate a guard more than once. A Pancake function is impure if it calls a foreign function, stores to memory, reads shared memory, raises, or writes a global, directly or through a callee.

An ACSL contract is lifted and rendered the same way. assigns \nothing; marks a C function pure, and a missing assigns clause counts as impure, since ACSL’s default permits every effect; the guard check currently runs for Pancake contracts only.

What fire verify proves

fire verify runs the contract prover first (Frama-C WP for a C import, pancake2viper for Pancake), then verifyta on the model that assumes the contracts. Both must pass: a model check over an unproved contract proves nothing about the code behind it.

Well-Formedness

After typing, fic checks four structural conditions that no typing rule expresses. Each one is a property the later stages rely on, and each is reported with the declaration it concerns. They are the checks of the CoreFi paper’s well-formedness, restricted to what a program text can violate: WF2 over the whole system, and three conditions on process bodies. (WF1 and the rest of WF3 are not checked here.)

A placeholder. Well-formedness checking is still under research. The checks below are what fic enforces today; which conditions the language needs, and how they are checked, may change.

WF2: the channel dependency graph is acyclic

A protection domain that receives from another waits for it. Draw an edge from each receiver to the sender it waits for: a cycle is a circular wait, a deadlock by construction. A unidirectional channel contributes one edge, receiver to sender; a bidirectional channel (<->) contributes both, so every bidirectional channel fails WF2. Parallel channels between one ordered pair of PDs are one edge.

error: WF2 violation: channel dependency graph contains a cycle:
ping → pong → ping (via channels: ball, ball)
 --> pingpong.fis:9:1
  | Chan ball = ping <-> pong;

The chain of the data-diode demo, eth_outer --> dd --> eth_inner, has no cycle and passes.

WF2 is a structural over-approximation: it also rejects programs that are deadlock-free under a fair scheduler. When deadlock-freedom is established another way, typically by model-checking the UPPAAL model fire build writes with fire verify, skip the check with --allow-wf2-cycles (or allow_wf2_cycles = true under [run.target] in fire.toml). The pingpong and pingpongpan demos do exactly this, and their spec/*.q files state the deadlock property instead.

Tail recursion

A process may refer to itself or to another process only as the last thing it does. The reference then compiles to a jump back to a process’s head and the control graph stays finite; a reference followed by more work would need a return stack.

proc Notified() { ball? -> Notified(); ball! -> Skip; }   // rejected
proc Notified() { ball? -> ball! -> Notified(); }         // accepted

error: process `Notified` is referenced in non-tail position inside
`Notified` — its continuation would need a return stack

A default branch and receives

The default arm of a choice runs when no branch’s guard holds. Beside a default, a branch that begins with a receive on a buffered channel fires when its ring holds a value, and the default only when the ring is empty: fic guards the receive with the ring’s state. That is a receive that gives up, as sDDF’s copier drops a frame when its client has no free buffer.

A signal receive or an IRQ await has no such state, so beside a default it is a branch with no guard, and a warning.

// d buffered, c a signal channel
proc Copy() { d?v -> Use(v) default drop -> Skip; }     // the default on an empty ring
proc Pick() { c? -> Skip default Skip; }                // warning: a branch with no guard

The notified handler is receive-headed

Microkit invokes notified with a message to handle. A process bound to microkit.notified that receives at all must therefore begin, on every path, with a receive (c?x) or an interrupt await (irq?N), through [], the left of ; and a helper process’s body, and with no guard and no default at the top. Otherwise the handler could run without consuming the message that woke it and never return to the kernel. A notified that never receives (a PD that only sends) needs no head.

A receive on a buffered channel may be guarded at the head: its ring is tested on every pass, guard first, so while the guard is false its values stay queued. A driver holds back this way while its device’s queue is full: [eth.rx_room()] free?b -> ….

@bind(microkit.notified)
proc Notified() { ball! -> ball? -> Skip; }   // rejected: starts with a send
@bind(microkit.notified)
proc Notified() { Skip; }                     // accepted: never receives
@bind(microkit.notified)
proc Notified() { ball? -> ball! -> Notified(); }   // accepted

error: process `Notified` bound to `microkit.notified` is not receive-headed:
each path at its head must begin with a receive (`c?x`) or an IRQ await
(`irq?N`) — the kernel invokes it for a message

A signal receive (c? on an unbuffered channel) or an IRQ await anywhere but the head is a warning: no notification arrives inside the invocation, so the handler would wait there for the next one, and any other notification meanwhile is dropped. A receive on a buffered channel may sit anywhere: it tests its ring, which the generated notified does on every pass, whichever channel notified. The echo server’s copier takes a frame at the head and then waits for a free client buffer this way.

Where the checks run

fic --check runs all four after typing, and every backend assumes them. The process-body checks run first, then the entry-point binding, the contract read and information flow; WF2 runs last.

Information Flow

Memory regions and the mappings that expose them carry a security label, Low or High, on the two-point lattice Low ≤ High. fic checks one rule over them.

A placeholder. Information-flow checking is at an initial stage, still under research. The rule below is what fic checks today, not a guarantee that High data cannot reach Low: flows through expressions, channels and foreign code are not checked.

A mapping’s label must be at least its memory region’s.

A High region is therefore never read through a Low mapping: High data cannot reach a context that is allowed to see only Low.

// .fis
High MemoryRegion secret(0x1000);
Low  MemoryRegion open(0x1000);

// .fi
High Mapping a(secret, "r");     // accepted: label matches
High Mapping b(open, "rw");      // accepted: upward, Low data seen as High
Low  Mapping c(open, "r");       // accepted
Low  Mapping d(secret, "r");     // rejected: a High region through a Low mapping

error: information flow violation: High memory region 'secret' is
accessed through Low mapping 'd'
 --> p.fi:1:1
  | Low Mapping d(secret, "r");

An unlabelled region or mapping is Low. The check reports one error per offending mapping, at the mapping, in the .fi that declares it.

What the labels do and do not cover

  • Labels sit on regions and mappings. A protection domain carries no label of its own: what a PD can see is exactly what it maps.
  • A channel buffer’s mapping takes its region’s label, so only a program’s own Mapping can violate the rule.
  • The check is on mappings only. It does not follow values between variables or across channels, and a channel carries no label.

The data diode

The data-diode demo labels the ring its outer side writes Low and the ring its inner side reads High, with one forwarding PD between them:

Low  MemoryRegion eth_outer_output(0x200000, 0x200000);
High MemoryRegion eth_inner_input(0x200000, 0x200000);

Chan o2d = eth_outer --> dd via eth_outer_output<Slot>;
Chan d2i = dd --> eth_inner via eth_inner_input<Slot>;

Frames enter on the Low side and leave on the High side. The rule keeps the labelling honest: the High ring can never be mapped with a Low label, by any program. It does not by itself make the diode one-way. That direction is the declared topology (-->, outer to inner, and no channel back), which fic --emit=dot draws and the WF2 check keeps acyclic, but which the information-flow check does not inspect.

fic --check runs this check after typing and the well-formedness checks.
