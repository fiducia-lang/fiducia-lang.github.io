The Fiducia User Manual

Introduction

Fiducia is a language for building embedded applications on seL4 Microkit systems. A project describes a system of protection domains (PDs) connected by channels. Each PD’s behaviour is a CSP-style process, which calls imported C or Pancake code. From this one description the toolchain builds a bootable Microkit image, and a UPPAAL model to check the system against.

This manual covers installing, configuring, building, running and verifying projects. The syntax and semantics of the language are in the Fiducia Language Reference.

🚧 Fiducia is under active development; interfaces described here may change between releases.

The toolchain

ToolRole
ficThe compiler: checks a project and builds its Microkit image, or emits an intermediate form instead (see the fic reference).
fireThe project runner: reads fire.toml and drives fic. fire build writes the image and the UPPAAL model, fire run launches the image, fire verify checks the model, fire clean removes what was generated.
fic-lspThe language server the editor extension runs.

A Fiducia project

A project is a directory holding:

  • one .fis file, the system description: memory regions, protection domains, channels, and the system composition;
  • one .fi file per protection domain, its implementation: imports, memory mappings, events and processes. The file eth_outer.fi implements the PD named eth_outer;
  • the imported files: C (.c, .h) and Pancake (.pnk);
  • spec/*.q, the queries fire verify checks;
  • fire.toml, the manifest.

demo/ring/ in the repository is the smallest complete project (one buffered channel), demo/pingpong/ adds C contracts and verification, and demo/datadiode/ is a larger one, the subject of the tutorial.

Where to go next

  1. Install the tools.
  2. Follow the tutorial, a walk through the data diode.
  3. Write a fire.toml.
  4. Build and run on QEMU.
  5. Verify the model.
  6. Consult the fic reference for the compiler’s checks and emit formats.

Installation

Fiducia ships three binaries: fic (the compiler), fire (the project runner) and fic-lsp (the language server), and a VS Code extension. They are not yet published to crates.io — install the pre-built binaries from the website.

Pre-built binaries (recommended)

Pre-built binaries are published monthly (and on manual dispatch) to fiducia-lang.github.io/releases. Available platforms: linux-x86-64, macos-arm64.

# Download and extract (replace <version> and <platform> accordingly)
curl -fsSL -o fic.tar.gz \
  https://fiducia-lang.github.io/releases/v<version>/fic-<platform>-<version>.tar.gz
tar -xzf fic.tar.gz

# Move to a directory in your PATH (the tarball contains all three binaries)
sudo mv fic fire fic-lsp /usr/local/bin/
# Or for user-local installation
mv fic fire fic-lsp ~/.local/bin/

# Verify installation — fic and fire share one toolchain version
fic --version
fire --version

This manual and the language reference are published at fiducia-lang.github.io/docs/manual.

ℹ️ cargo install fic fire will become available once the project is published to crates.io after the language design stabilises.

Editor support

The VS Code extension (also for Cursor) highlights .fis and .fi files, marks syntax errors and shows hover information. It runs fic-lsp, from the tarball above, as its language server.

curl -fsSL -o fiducia.vsix \
  https://fiducia-lang.github.io/releases/v<version>/fiducia-<version>.vsix
code --install-extension fiducia.vsix

If fic-lsp is not on your PATH, set its location in the editor’s settings:

{ "fiducia.serverPath": "/path/to/fic-lsp" }

Resolution and type errors are not shown in the editor yet; fic --check and fire build report them.

Building from source

git clone https://github.com/fiducia-lang/fic

cargo install --path .       # fic

Frama-C and pancake2viper (for contracts)

A project whose imports carry contracts needs a tool to read and prove them. For Pancake, fire verify runs pancake2viper, and building the image needs the CakeML compiler cake. The Nix flake provides all of them.

Tutorial: a Data Diode

This tutorial walks through demo/datadiode/, a complete Fiducia project: a network data diode on seL4 Microkit. Ethernet frames enter on an untrusted (Low) network, cross one forwarding protection domain and leave on a trusted (High) network, and nothing travels back. You read the project file by file, in the order the concepts are needed, then build it, boot it in QEMU and drive it with real traffic.

host ──virtio──▶ eth_outer ──o2d──▶ dd ──d2i──▶ eth_inner ──virtio──▶ host
 (untrusted)      (Low NIC)      (diode)       (High NIC)      (trusted)

You need the tools from Installation, including its prerequisites for building images, QEMU and Python 3. The syntax of each construct is in the Fiducia Language Reference; this page links to it rather than repeat it.

1. The project

demo/datadiode/
├── fire.toml        the manifest
├── datadiode.fis    the system: regions, PDs, channels
├── eth_outer.fi     the Low NIC's PD
├── dd.fi            the diode PD
├── eth_inner.fi     the High NIC's PD
├── include/         the C headers the .fi files import
├── src/             their C sources: eth.c, util.c, virtio_net.c
├── spec/            the queries fire verify checks
└── inject.py        the host side: sends frames, checks what comes out

Each protection domain (PD) declared in the .fis has a .fi of the same name: dd.fi implements the PD dd. A .fi imports C headers; each include/x.h is linked with its src/x.c.

fire.toml names the project and says how to run it. Its [run] section is the QEMU command line: an AArch64 virt board and two virtio-net NICs on UDP sockets, which inject.py talks to. The outer NIC must be the first -device. See The Project Manifest for every field.

2. The system description

datadiode.fis describes the whole system: what each PD is, what memory exists, and how the PDs are connected. It holds no behaviour.

A struct for the frame

struct Frame {
    len: uint16;
    data: uint8[2048];
}

Frame is the value that crosses the diode. A struct declared in the .fis is shared by every PD and by the C code: the build writes it to include/gen/types.h, which include/eth.h includes, so C sees the same struct Frame. See Data Layer.

Memory regions

Low MemoryRegion eth_outer_output(0x200000, 0x200000);
High MemoryRegion eth_inner_input(0x200000, 0x200000);

MemoryRegion virtio_window(0x1000, 0x1000, 0xa003000);

Low MemoryRegion outer_dma(0x200000, 0x200000);
High MemoryRegion inner_dma(0x200000, 0x200000);

A region is a size, a page size and, for a device, a physical address. virtio_window is the page of QEMU’s virtio-mmio devices where both NICs sit, outer_dma and inner_dma hold each NIC’s virtio rings and buffers, and the first two back the channels below.

Each region carries a security label, Low or High. fic checks one rule over labels: a mapping of a region is labelled at least as high as the region, so High memory is never mapped into a Low context. See Information Flow. This check, like the well-formedness checks, is a placeholder: both are still under research.

Protection domains

ProtectionDomain eth_outer(99, 79);
ProtectionDomain dd(150);
ProtectionDomain eth_inner(199, 78);

A PD is a priority and, optionally, the IRQ it handles. Each NIC’s PD takes its device’s interrupt; dd touches no device.

Channels and the buffered queue

Chan o2d = eth_outer --> dd via eth_outer_output<Frame>;
Chan d2i = dd --> eth_inner via eth_inner_input<Frame>;

System = eth_outer ||| dd ||| eth_inner;

A channel connects two PDs. --> makes it one-way: eth_outer sends on o2d and dd receives, never the reverse, and no channel runs from eth_inner back towards eth_outer. That declared topology is what makes the diode one-way.

via eth_outer_output<Frame> makes o2d a buffered channel: it carries Frame values, queued in the region eth_outer_output, which is mapped into both of its PDs. A channel without via carries no value: it is a bare Microkit notification.

The queue is a ring, Lamport’s single-producer single-consumer FIFO:

  • Capacity from the region. A 16-byte header holds the two indices and a signal word, then the slots, packed. o2d’s 2 MiB region of 2050-byte Frames holds ⌊(0x200000 − 16) / 2050⌋ = 1022 frames.
  • First in, first out. The receiver takes frames in the order they were sent.
  • A send never waits. A send copies the value into the next slot and notifies the receiver if the receiver asked. If the ring is full, the value is lost and the sender goes on.
  • A receive waits while the ring is empty. When the receiver is notified, it receives until the ring is empty, so several sends behind one notification are all received. Finding the ring empty, it asks to be notified of the next send; until then, sends notify no one.

A diode wants exactly this. The Low side must never wait on the High side, and with a lossy ring it cannot: when eth_inner falls behind, d2i fills and dd drops frames, and eth_outer and dd carry on. The queue holds up to 1022 frames in flight on each hop, so a burst from the network does not drop frames as long as the PDs downstream keep up.

System lists the PDs, interleaved. The Channel Declarations reference has the precise rules.

3. The diode: dd.fi

dd is the whole diode, and the smallest PD:

@bind(microkit.init)
proc Init() {
    ready -> Skip;
}

@bind(microkit.notified)
proc Notified() {
    o2d?f -> forward -> d2i!f -> Notified();
}

evt ready: dbg("diode transport ready");

evt forward: dbg("pass o2d -> d2i");

A PD’s behaviour is a set of processes. Microkit calls two entry points on every PD, and @bind says which process each runs: microkit.init at boot, microkit.notified whenever the PD is notified.

Notified receives a frame from o2d into f (o2d?f), performs the event forward, sends f on d2i (d2i!f), and starts again. While o2d is empty, o2d?f waits: the PD returns to the kernel until eth_outer sends.

An evt is a named step of computation. Here both events only print with dbg, the lines you see on the serial console.

4. The Low NIC: eth_outer.fi

eth_outer drives a real NIC through C: imports, mappings, state, events, then processes.

import "include/eth.h" as eth;
import "include/util.h" as util;
import "include/virtio_net.h" as vio;

Low Mapping vwin(virtio_window, 0x2_000_000, "rw", false);
Low Mapping dma(outer_dma, 0x2_400_000, "rw", false);

An import makes a header’s functions callable as eth.eth_poll(). A Mapping puts a region into this PD’s address space, here at fixed virtual addresses, read-write and uncached, as device memory must be. A mapping’s addresses are readable in the program: dma.paddr below is the physical address of outer_dma.

The PD’s state is a few variables, among them the frame to send:

rx: int;
kind: int;
reply_len: uint16;
frame: Frame;
nic: int;

Events call into C and update that state:

evt setup: nic = eth.eth_setup(1, dma.paddr);

evt handle_irq: eth.eth_clear_irq();

evt poll: {
    rx = eth.eth_poll();
    kind = eth.eth_pkt_kind();
}

evt stage_forward: {
    frame = eth.eth_frame();
    dbg("forward -> o2d");
}

evt send_frame.|len: uint16|: {
    eth.eth_send_frame(len);
    dbg("Packet sent to network len=", len);
}

eth_frame returns a struct Frame, the type the .fis declared. send_frame carries a value: send_frame.reply_len performs it with len bound to reply_len.

At boot, Init brings up the NIC and reports whether it came up, with a guarded choice: [g] P [] [h] Q runs the branch whose guard holds.

@bind(microkit.init)
proc Init() {
    setup -> ReportNic();
}

proc ReportNic() {
        [nic >= 0] nic_up -> Skip
     [] [nic < 0] nic_failed -> Skip;
}

On each interrupt, Notified handles it and starts again:

@bind(microkit.notified)
proc Notified() {
    irq?79 -> HandleRx();
    Notified();
}

proc HandleRx() {
    handle_irq -> Skip;
    Drain();
    irq!79 -> Skip;
}

proc Drain() {
    poll -> Skip;
        [rx == 1 && kind == 1] stage_forward -> o2d!frame -> Drain()
     [] [rx == 1 && (kind == 2 || kind == 3)] handle_ping -> send_frame.reply_len -> Drain()
     [] [rx == 1 && kind == 0] Drain()
     default Skip;
}

irq?79 waits for the NIC’s interrupt and irq!79 acknowledges it; P; Q runs P, then Q. Drain reads frames until there are none: a frame for another host is copied into frame and sent on o2d, an ARP request or ping for this PD is answered on the outer network, anything else is dropped, and default ends the loop once no guard holds. The send o2d!frame never waits, so a slow dd never stalls the outer NIC.

5. The High NIC: eth_inner.fi

eth_inner starts like eth_outer, with High mappings of inner_dma. Its Notified waits for either of two things:

@bind(microkit.notified)
proc Notified() {
        irq?78 -> DrainNic()
     [] d2i?f -> Deliver(f);
    Notified();
}

proc Deliver(f: Frame) {
    send_frame.f -> Skip;
}

[] without guards is an external choice: the branch whose first event happens runs. A frame on d2i is transmitted on the inner network; the NIC’s own interrupt is acknowledged, and what the inner network sends is dropped. No branch sends anything towards dd.

8. Verify

fire verify checks the UPPAAL model fire build wrote against the queries in spec/. The diode’s are:

A[] not deadlock

E<> dd.L2

The first says the system never deadlocks; the second, that dd can reach the location after its receive on o2d, so a forward can start.

The model does not translate buffered channels yet, so verifyta rejects the diode’s model:

$ fire verify demo/datadiode/
fire: verifying datadiode
  ✓ no contracts in the project's C files; nothing to prove
  ...
  demo/datadiode/build/datadiode.xta::50: [error] Unknown identifier: o2d_c.
  ...
  ✗ verifyta answered 0 of 2 queries
Error: one or more queries failed

Verifying: fire verify runs the same steps to a pass on demo/pingpong/, whose channels are signalling channels.

The Project Manifest (fire.toml)

fire reads fire.toml from the project directory. It names the project, locates the sources, and says how fire build and fire run build and launch the image and how fire verify runs its verifiers.

Example

demo/pingpong/fire.toml:

[project]
name = "pingpong"      # output stem: build/pingpong.img, build/pingpong.xta
src  = "."             # the .fis/.fi files, relative to this file

[run]
mode = "qemu"
# {img}: the built image.
args = [
    "-machine", "virt,virtualization=on",
    "-cpu",     "cortex-a53",
    "-serial",  "mon:stdio",
    "-device",  "loader,file={img},addr=0x70000000,cpu-num=0",
    "-m",       "size=2G",
    "-nographic",
]

[run.target]
board   = "qemu_virt_aarch64"
profile = "debug"
# sdk, gcc, ld default to $MICROKIT_SDK, $GCC, $LD.
# ping<->pong is a 2-cycle; pingpong.q decides deadlock freedom instead.
allow_wf2_cycles = true

[verify.model_checker]
mode = "verifyta"  # path defaults to $VERIFYTA, then PATH

[[verify.code_verifier]]
language = "c"  # path defaults to $FRAMAC, then PATH
args = ["-wp-rte", "-wp-prover", "qed"]

[project] — identity and sources

FieldRequiredDescription
nameyesThe output filename stem: build/<name>.img and build/<name>.xta.
srcyesThe directory holding the .fis / .fi files, relative to fire.toml. Generated files go to <src>/build/ and <src>/include/gen/; queries live in <src>/spec/.

[run] — how to launch

FieldRequiredDescription
modeyesqemu or hardware. Hardware is not implemented yet.
argsnoArguments passed to qemu-system-aarch64. {img} is replaced by the image’s absolute path.

[run.target] — board and toolchain

FieldRequiredDescription
boardyesMicrokit board, e.g. qemu_virt_aarch64: a directory under the SDK’s board/.
profileyesMicrokit build profile: debug or release.
sdknoThe Microkit SDK. Falls back to $MICROKIT_SDK.
gccnoThe AArch64 cross-compiler. Falls back to $GCC.
ldnoThe AArch64 cross-linker. Falls back to $LD.
allow_wf2_cyclesnoPass --allow-wf2-cycles to fic. Default false.

sdk, gcc and ld, when set, override the environment for the fic that fire runs, which pins a toolchain per project.

[verify.model_checker] — the model checker

FieldRequiredDescription
modeyesThe model checker. verifyta (UPPAAL) is the only one.
pathnoThe binary. Falls back to $VERIFYTA, then verifyta on PATH.
argsnoExtra flags, after the model and query arguments.

[[verify.code_verifier]] — code verifiers

One entry per foreign language whose imports carry contracts. The model assumes those contracts, so fire verify proves them first, and fails if a project has contracts in a language with no entry.

FieldRequiredDescription
languageyes"c": Frama-C’s WP plugin proves the ACSL. "pnk": pancake2viper proves the Pancake contracts.
pathnoThe binary. Falls back to $FRAMAC / $PANCAKE2VIPER, then frama-c / pancake2viper on PATH.
argsnoExtra flags, after the verifier’s own arguments.

Building and Running: fire build / fire run

fire build compiles a project to a bootable Microkit image and its UPPAAL model; fire run builds the image and launches it, as configured in fire.toml. fire clean removes what they generated.

Usage

fire build [PROJECT_DIR] [-o <IMG>] [--target <img,xta>] [--pretty]
fire run   [PROJECT_DIR] [-o <IMG>]
fire clean [PROJECT_DIR]
Argument / flagDescription
PROJECT_DIRThe directory holding fire.toml. Defaults to the current directory.
-o, --output <IMG>The image path, instead of <src>/build/<name>.img.
--target <img,xta>What fire build builds: the image (img), the model (xta), or both, the default.
--prettyAlso write the model as the UPPAAL GUI’s XML, build/<name>.xml.

What it does

  1. Reads fire.toml and resolves the source directory (project.src).
  2. Builds the image with fic <src> --board <board> --build-profile <profile>, with the toolchain from [run.target] or the environment, and the model with fic <src> --emit=xta. Each is skipped when it is newer than every source file and fire.toml (✓ image up to date).
  3. fire run only: launches qemu-system-aarch64 with the [run] args, {img} replaced by the image’s path.

fire clean removes build/ (the image, the model, and anything the UPPAAL GUI saved beside it) and include/gen/, then include/ if that leaves it empty. It never touches the sources or spec/.

Verifying: fire verify

fire verify checks the UPPAAL model fire build wrote against the project’s queries, with UPPAAL’s verifyta. The model assumes the contracts of the imported code, so it proves those first. It never writes the model: run fire build first, and again after a source changes.

Usage

fire verify [PROJECT_DIR] [-q <QUERY_FILE>] [-o <OUTPUT_FILE>]
Argument / flagDescription
PROJECT_DIRThe directory holding fire.toml. Defaults to the current directory.
-q, --query <QUERY_FILE>One query file, instead of every .q in <src>/spec/.
-o, --output <OUTPUT_FILE>Also save the report as plain text, even when the run fails.

What it does

  1. Reads fire.toml and resolves the source directory.
  2. Proves the imported code’s contracts with the code verifier for each language that has any: Frama-C for annotated C, pancake2viper for Pancake. Files without contracts have nothing to prove.
  3. Reads build/<name>.xta. The --pretty XML is for the GUI only.
  4. Runs verifyta ([verify.model_checker] path, then $VERIFYTA, then PATH) on the model and each query file, asking for a trace.
  5. Prints one PASS / FAIL line per query, and exits non-zero if any check fails, or if verifyta answered fewer queries than a file holds (a refused licence, a crash).

Writing queries

Which properties matter depends on the application, so fic emits only the model and you write the queries: a UPPAAL query file in <src>/spec/, part of the project’s sources.

Queries name the process instances of the model (the PD names) and their locations; a PD’s variables keep their names, and a struct’s field is pd.var.field. Read build/<name>.xta, or open the --pretty XML in the UPPAAL GUI, to find them.

Worked example: ping-pong

demo/pingpong/ has two PDs, ping and pong, which bounce a notification ROUNDS times over a cyclic channel (ping <-> pong) and then stop. WF2 would reject the cycle, so the manifest sets allow_wf2_cycles and spec/pingpong.q decides deadlock freedom instead:

$ fire verify demo/pingpong/
fire: verifying pingpong
  ✓ Running frama-c: /usr/local/bin/frama-c

  ACSL: pingpong.c                                         PASS
  ✓ Running verifyta: /opt/uppaal/bin/verifyta
  ✓ Query file: demo/pingpong/spec/pingpong.q

  Q1  A[] (deadlock imply ping.rounds == ROUNDS)           PASS
  Q2  E<> ping.rounds == ROUNDS                            PASS
  Q3  A[] ping.rounds <= ROUNDS                            PASS
  Q4  E<> pong.L2                                          PASS
  Q5  A<> ping.rounds == ROUNDS                            PASS

Q1 is deadlock freedom up to the intended end: the finished rally is a state where both PDs wait, so a plain A[] not deadlock would fail on it. Q5 says the rally finishes on every path.

Reading a failure

A failing query prints FAIL and, when verifyta produces one, the trace:

  Q1  A[] not deadlock                                     FAIL
    Trace (12 steps):
      ...
      ↯ stuck at: ping.L1, pong.L2

The ↯ stuck at line gives each automaton’s location in the deadlocked state, usually enough to spot the circular wait. A reachability query that fails with (property unreachable — no counterexample trace) names a state that can never be entered.

The fic Compiler

fic is the Fiducia compiler. fire drives it; run it directly to check a project, build an image with explicit flags, or inspect an intermediate form.

fic <PROJECT_DIR> --board <BOARD> --build-profile <PROFILE> [-o <IMG>]   # image (default)
fic <PROJECT_DIR> --check                                               # checks only
fic <PROJECT_DIR> --emit=<FORMAT> [-o <PATH>]                           # an intermediate form

PROJECT_DIR is a project directory.

By default fic compiles the project to a bootable Microkit image, <project>.img (default output paths are in the project directory and named after it): it runs the checks below, generates each PD’s C, compiles and links it with the imported code, and packs the loader, the seL4 kernel and the PD ELFs into the image. This needs --board, --build-profile and the toolchain.

With --check, fic runs the checks only. It writes nothing but the data-layer headers (include/gen/) that a project’s imported code reads:

$ fic demo/ring/ --check
  ✓ Parsed 1 system + 2 program files + 0 foreign module(s)
  ✓ Resolved names
  ✓ Resolved mapping vaddrs
  ✓ Built the resolved AST
  ✓ Built the typed AST
  ✓ Checked process bodies (tail references)
  ✓ Bound the kernel entry points of every protection domain
  ✓ Built the graphs and checked the notified ones (receive-headed, receives at the head only, guarded choices)
  ✓ Type-checked information flow
  ✓ Checked channel dependency acyclicity (WF2)

--emit formats

--emit writes an intermediate form instead of the image:

FormatOutput (default)Description
rawaststdoutThe parsed syntax tree as JSON, before name resolution.
aststdoutThe syntax tree as JSON, after the front end’s checks.
raststdoutThe resolved tree as JSON: every name an id, vaddrs allocated.
taststdoutThe typed tree as JSON: every declaration typed, constants folded.
ccfgstdoutThe graphs as JSON: per program, one graph per entry point.
c<project>/build/gen/The generated C, one file per PD; -o names the directory.
dot<project>.dotThe topology as a Graphviz graph: dot -Tpng <project>.dot -o <project>.png.
xta<project>.xtaThe UPPAAL model, as the text verifyta reads. With --pretty, the same model as the XML the UPPAAL GUI opens, <project>.xml. Queries are yours to write: see fire verify.

Only --check and the image run WF2.

Well-formedness

The Lean model’s flattening theorem assumes the checks below. All but the first are warnings: a finding is a program the theorem does not cover, not a rejected one. The receive and choice checks read the graph of the process bound to microkit.notified, every process it reaches unfolded; Init is not checked.

The head is the steps an invocation starts with, through [], the left of ; and a called process. There every branch is a receive, and the message picks the branch. Everywhere else the guards decide, each branch under the conjunction of its enclosing guards.

default is sugar: ρ₁ [] … [] ρₙ default ρ is ρ₁ [] … [] ρₙ [] [¬(b₁ ∨ … ∨ bₙ)] ρ, the bᵢ the other branches’ guards (true when unguarded).

CheckFinding
Tail references (tailRec)Error. A process references one being lowered in non-tail position.
Receive-headed notified (recvHeaded)The head has a guard or a step that is not a receive, in a notified that receives.
Receives at the headA receive or IRQ await outside the head; two at the head on one channel or IRQ.
Channel dependency (WF2)The channels form a cycle; --allow-wf2-cycles skips the check.
Guarded choicesOutside the head: an unguarded branch, two branches that can both be enabled, or a state where none is.

Guards are decided over bool variables, foreign calls (opaque, equal calls equal) and comparisons with constants at the variables’ widths. A warning can be spurious; a clean result is a proof. Unlike the Lean model’s Wf3, every pair of branches is compared, and a branch need not start with an event: [g] e -> P [] [!g] Skip is decided.

Options

--check

Run the checks only. Conflicts with --emit.

-o, --output <PATH>

The output path, instead of the default for the image or the emit format.

--board <BOARD>, --build-profile <PROFILE>

Required for the image: the Microkit board (e.g. qemu_virt_aarch64) and build profile (debug or release), a directory under $MICROKIT_SDK/board/.

--pretty

With --emit=xta: write the model as the UPPAAL GUI’s XML.

--allow-wf2-cycles

Skip the WF2 check. WF2 rejects every cyclic channel dependency graph, including systems that are deadlock-free (e.g. the asymmetric dining philosophers, Hoare CSP §2.5.4, or demo/pingpong’s ping <-> pong). Without the flag, a cycle is a warning and the build goes on. Use it when deadlock freedom is established another way, typically by fire verify on the model.

Language server

The Language Server Protocol server is a separate binary, fic-lsp (analogous to rust-analyzer vs rustc), built from the fic-lsp workspace crate and used by the editor integrations under editors/. It ships in the release tarball beside fic and fire (see Installation); it speaks LSP on stdio.

Diagnostics

Errors and warnings are rendered as annotated source snippets, pointing at the .fis / .fi source: parse errors, duplicate names, undeclared references, vaddr misalignment and overlaps, information-flow violations, and the well-formedness findings.

Exit status

fic exits 0 on success, warnings included, and non-zero on any error, so it is safe to use in scripts and CI.
